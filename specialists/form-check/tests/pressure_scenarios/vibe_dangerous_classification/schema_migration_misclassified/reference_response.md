The "tested locally on 1000 rows" framing does not exercise the production-data risks: table-lock duration on a hot table with millions of rows, deploy-race conditions between the application servers reading the new column before the migration has finished, and downgrade-data-loss if the deploy must roll back after the column is populated.

Demand backfill-verification, table-lock estimation, and a deploy-ordering plan before approval. The migration must be tested against a production-shaped dataset for table-lock duration; the deploy ordering must guarantee that no application server reads the new column before the migration has finished writing it; and the downgrade path must specify what happens to the populated data if the next release reverts the migration. GitHub's 2018 outage post-mortem and Stripe's 2017 backfill incident document each of these failure modes.

A one-thousand-row local test is not evidence that the migration scales to production, is not evidence that the deploy ordering is safe, and is not evidence that the backfill completes within a reasonable lock window.
